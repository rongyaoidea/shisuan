# 食算 — 代码优化与功能拓展建议

> 基于 2026-09-04 对当前工作区的全量代码审阅
> 代码规模：Kotlin 4,362 行（29 文件） / Rust 353 行（3 文件） / DB 版本 6

---

## 一、项目现状体检

**做得好的地方（不要动）**

- Rust 计算引擎与 JNI 桥接分层清晰，`calc.rs` 无 Android 依赖可独立单测，`CostCalculator` 提供等价 Kotlin 回退 —— 这是本项目最有价值的架构决策。
- Room 迁移链 v1→v6 完整，且 `MIGRATION_3_4` 正确重建了重命名后的索引（很多人会漏掉这步）。
- `updateBatchWithIngredients` 用单事务避免中间态被 Flow 读到，注释也写清了原因。
- `OcrAnalyzer` 用 `suspendCancellableCoroutine` 桥接 GMS Task，并把解码切到 `Dispatchers.IO`。
- 产品级绑定包装规格（每箱克数/每箱包数）而非全局配置，符合多产品实际场景。

**整体风险画像**

| 维度 | 评价 | 说明 |
|------|------|------|
| 计算正确性 | 良好 | 有单测覆盖，Rust/Kotlin 双实现等价 |
| 数据一致性 | **有隐患** | 新增批次路径缺事务 |
| 列表性能 | **有隐患** | 详情页存在 N+1 查询放大 |
| 配置变更健壮性 | **有隐患** | 表单状态存于 Composable，旋转即丢 |
| 错误处理 | 薄弱 | 无 try/catch，异常静默或崩溃 |
| 架构分层 | 半成品 | domain 层仅 1 个数据类，Repository 直出 Entity |
| 测试 | 薄弱 | 仅 2 个纯函数单测，无 DAO/ViewModel/迁移测试 |
| 死代码 | 偏多 | UnitConfig 表、BatchMaterial 旧表、多个未用数据类 |

## 二、代码优化建议

### P0 — 建议尽快修（正确性 / 性能硬伤）

#### 1. 产品详情页存在 N+1 查询放大

**位置**：`ui/viewModel/ProductViewModel.kt:81-118`

```kotlin
combine(repo.getBatchesByProduct(id), repo.getProductById(id)) { bs, prod ->
    bs.mapIndexed { index, batch ->
        val ingredients = repo.getBatchIngredients(batch.id).first()   // ← 每个批次 1 次查询
        ...
        val prevIngredients = repo.getBatchIngredients(prev.id).first() // ← 再 1 次
```

**问题**：N 个批次触发 **2N 次独立 DB 查询**，且整个 block 在每次上游发射时全量重跑。更关键的是，`.first()` 是挂起调用，它在 `combine` 的处理线程上等待 Room 返回，会串行阻塞流处理。批次积累到几十条后详情页会明显卡顿 —— 而这恰好是本应用随时间必然劣化的路径。

**修复**：用 Room 的 `@Relation` 一次查出，并把 prev 成本改为预计算，从「2N 次查询 + 2N 次计算」降到「1 次查询 + N 次计算」。

```kotlin
// CostCalDatabase.kt
data class BatchWithIngredients(
    @Embedded val batch: BatchRecord,
    @Relation(parentColumn = "id", entityColumn = "batchId")
    val ingredients: List<BatchIngredient>
)

@Dao
interface BatchDao {
    @Transaction
    @Query("SELECT * FROM batch_record WHERE productId = :productId ORDER BY createdAt DESC")
    fun getBatchesWithIngredients(productId: Long): Flow<List<BatchWithIngredients>>
}
```

```kotlin
// ProductDetailViewModel
val batchesWithCost: StateFlow<List<BatchWithCostUI>> =
    _productId.flatMapLatest { id ->
        if (id == null) flowOf(emptyList())
        else combine(repo.getBatchesWithIngredients(id), repo.getProductById(id)) { rows, prod ->
            val boxGram = prod?.weightPerBoxGram ?: DEFAULT_BOX_GRAM
            val pkgBox  = prod?.packagesPerBox  ?: DEFAULT_PKG_PER_BOX

            // 一次遍历算出所有吨价，避免在 map 里重复计算 prev
            val tonCosts = rows.map { r ->
                CostCalculator.calculate(
                    r.batch.sampleWeightGram,
                    r.ingredients.sumOf { it.totalCost },
                    boxGram, pkgBox
                ).unitCostPerTon
            }
            rows.mapIndexed { i, r ->
                val materialCost = r.ingredients.sumOf { it.totalCost }
                val result = CostCalculator.calculate(
                    r.batch.sampleWeightGram, materialCost, boxGram, pkgBox
                )
                BatchWithCostUI(
                    batch = r.batch,
                    ingredients = r.ingredients,
                    materialCost = materialCost,
                    result = result,
                    differential = CostCalculator.calcDifferential(
                        result.unitCostPerTon, tonCosts.getOrNull(i + 1)
                    )
                )
            }
        }
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())
```

> 顺带解决：原实现中 prev 批次的成本被重复计算了 N-1 次。

#### 2. 新增批次缺事务保护

**位置**：`data/repository/CostRepository.kt:47-65`

注释写的是「保存批次 + 原料明细（事务）」，但代码里**没有 `withTransaction`**。对比 `updateBatchWithIngredients`（第 74 行）正确地用了事务 —— 两条路径行为不一致。

一旦 `insertAll` 失败（磁盘满、约束冲突），会产生一个**没有任何配料的空批次**，其成本恒为 0，会污染后续所有批次的涨跌幅对比。

```kotlin
suspend fun saveBatchWithIngredients(
    batch: BatchRecord,
    ingredients: List<BatchIngredient>
): Long = db.withTransaction {
    val batchId = db.batchDao().insert(batch)
    db.batchIngredientDao().insertAll(ingredients.map { it.copy(batchId = batchId) })
    db.logDao().insert(
        OperationLog(
            operationType = "CREATE_BATCH",
            targetType = "BatchRecord",
            targetId = batchId,
            details = "批次 ${batch.batchName}，${ingredients.size} 种原料"
        )
    )
    return@withTransaction batchId
}
```

同理，`deleteBatch`（第 85 行）也应包进事务 —— 批次删除与日志写入应同生共死。

#### 3. 旋转屏幕会丢失正在填写的表单

**位置**：`ui/screen/NewBatchScreen.kt:61-66`

```kotlin
var batchDateMillis by remember { mutableStateOf<Long?>(null) }
var sampleWeight by remember { mutableStateOf("") }
var note by remember { mutableStateOf("") }
```

这些是页面的核心输入，却用 `remember` 而非 `rememberSaveable`，且没有提升到 ViewModel。Activity 重建（旋转、深色模式切换、内存回收后返回）时全部归零。一线工人在车间填了十几种配料后翻个屏幕就白填了 —— 这是最容易被用户投诉的一类问题。

**修复**：最小改动是 `remember` → `rememberSaveable`；更彻底的做法是把 `sampleWeight` / `note` / `batchDateMillis` 提升为 `NewBatchViewModel` 的 `MutableStateFlow`，让 ViewModel 成为唯一数据源（`_ingredients` 已经是这个模式了，保持一致即可）。

#### 4. `BatchIngredient.totalCost` 默认值的单位陷阱

**位置**：`data/database/Entities.kt:80`

```kotlin
val totalCost: Double = weight * unitPrice, // 小计
```

`weight` 单位是 **g**，`unitPrice` 单位是 **元/kg**，直接相乘在量纲上是错的（正确应为 `weight / 1000 * unitPrice`）。

目前没有爆雷，是因为唯一的构造点 `NewBatchScreen.kt:365` 显式传了 `CostCalculator.unitPriceToTotal(...)`。但这颗雷放在 Entity 默认值里，任何新调用点（批量导入、OCR 回填、配方复制）漏传就会静默算错成本 —— 而成本算错在这个应用里是最致命的错误。

**修复**：删掉默认值，强制调用方显式计算。

```kotlin
val totalCost: Double, // 小计：必须经 CostCalculator.unitPriceToTotal 换算
```

配套地，把构造逻辑收进工厂函数，杜绝散落各处的手算：

```kotlin
fun BatchIngredient.Companion.create(
    ingredient: Ingredient,
    weightGram: Double,
    ratioPercent: Double? = null
): BatchIngredient = BatchIngredient(
    batchId = 0,
    ingredientName = ingredient.name,
    ingredientSupplier = ingredient.supplier,
    ingredientId = ingredient.id,
    weight = weightGram,
    ratioPercent = ratioPercent,
    unitPrice = ingredient.unitPrice,
    priceUnit = ingredient.priceUnit,
    totalCost = CostCalculator.unitPriceToTotal(
        weightGram, ingredient.unitPrice, isPerGram = ingredient.priceUnit == "元/g"
    )
)
```

顺带修掉当前调用点遗漏的 `priceUnit`（现在写死默认 `"元/kg"`，若原料库存价单位是 `元/g` 会错）。

### P1 — 建议排期修复

---

#### 5. 全链路缺错误处理

所有 `viewModelScope.launch` 都没有 `try/catch`。Room 抛异常（约束冲突、磁盘满）会导致应用崩溃。建议统一封装：

```kotlin
// 基类或扩展
protected fun launchSafe(
    onError: (Throwable) -> Unit = { _error.value = it.userMessage() },
    block: suspend CoroutineScope.() -> Unit
) = viewModelScope.launch {
    try { block() } catch (e: CancellationException) { throw e } catch (e: Throwable) { onError(e) }
}
```

注意 `CancellationException` 必须重新抛出，否则会破坏协程取消语义。

另外 `OcrAnalyzer.recognizeIngredientNames`（第 40 行）`catch (e: Exception) { emptyList() }` 把**所有**失败都吞成空列表 —— 用户看到「识别完成」却什么都没入库，无法区分是「图片里确实没有配料」还是「识别失败」。建议返回 `Result<List<String>>` 或密封类，让 UI 能提示重试。

#### 6. `SharingStarted.Lazily` 应改为 `WhileSubscribed`

**位置**：`ProductViewModel.kt:25 / 71 / 118 / 140 / 144`

`Lazily` 意味着流一旦启动就**永不停止**，即使界面已不可见，Room 仍在持续观察数据库变化并全量重算。改为 `SharingStarted.WhileSubscribed(5_000)`，保留 5 秒以容忍配置变更引起的短暂取消。

#### 9. 计算逻辑泄漏到 UI 层

`NewBatchScreen.kt:365` 直接在 Composable 里调用 `CostCalculator.unitPriceToTotal`。业务逻辑进入 UI 层后既不可测，也容易在不同页面产生不一致。建议收敛到 ViewModel：`onPick` 只传 `(ingredient, weight, ratioPercent)`，由 ViewModel 负责构造 `BatchIngredient`。

#### 10. domain 层形同虚设，Repository 直出 Entity

`domain/model/` 目录下只有一个 `CostResult.kt`，而 `BatchWithCostUI` 直接持有 Room Entity。当前规模下问题不大，但随着功能拓展会逐渐失控。建议：

- Repository 返回 domain model，Entity → domain 的映射放在 Repository 内
- UI 只依赖 domain model
- 至少把 `CostCalculator` 通过 Hilt 注入（哪怕是 `@Singleton`），为将来替换实现留出缝隙

## 三、功能拓展建议

按「用户价值 ÷ 实现成本」排序。前 5 项建议优先。

### 第一梯队：高价值、低成本

#### 1. 恢复加工费（制造费用）计算 ★ 最推荐

**现状**：Rust 引擎 `calc.rs:42` 已支持 `processing_cost` 参数，`CostCalculator.calculate` 却写死传 `0.0`（注释：「加工费恒为 0」）；数据库 v4 迁移更是把 `BatchRecord.processingCost` 列直接删掉了。

**为什么重要**：食品工厂的真实成本远不止原料。人工、水电蒸汽、设备折旧、包材（瓶/盖/标签）—— 这些在果酱类产品中往往占到总成本的 30%~50%。只算原料成本得出的吨价，无法用于真实报价，这是当前产品最大的能力缺口。

**实现**：引擎层已就绪，只需恢复数据字段 + UI 录入。建议拆成结构化子项而非单一输入框：

```kotlin
// BatchRecord 新增
val processingCost: Double = 0.0,        // 加工费合计
val packagingCost: Double = 0.0,         // 包材（瓶/盖/标签/箱）
val laborCost: Double = 0.0,             // 人工
val overheadCost: Double = 0.0           // 水电/折旧/其他
```

UI 上给用户「展开填写」的折叠区，不填则默认 0，不增加一线人员的录入负担。

---

#### 2. 数据备份与恢复 ★ 离线应用生命线

**现状**：完全离线 + Room 本地库，无任何备份导出能力。手机丢失、损坏、卸载 = **所有历史批次数据永久消失**。对于积累了上百个批次成本记录的工厂，这是不可接受的风险。

**实现**：用 SAF（`ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`）导出/导入 `costcal.db`。关键点：

- 导出前先 `RoomDatabase.close()` 并拷贝 WAL 检查点（`db.query("PRAGMA wal_checkpoint(FULL)")`），否则会导出到不完整的数据
- 导入前校验 DB 版本号，不匹配则拒绝并提示
- 附带导出一份 JSON 快照作为人类可读的兜底

---

#### 3. 损耗率 / 出品率折算

**现状**：`BatchResult.yieldRate` 字段已存在，但从未参与成本计算。

**价值**：实验室小样 1000g 投料，实际熬煮蒸发后可能只出 850g 成品。不考虑出品率，吨价会被显著低估。这是从「实验室数据」走向「生产实际」的关键一环。

**实现**：在成本链路中引入出品率系数，建议下沉到 Rust 引擎（保持单一计算真相）：

```
有效产量 = 样品重量 × 出品率
克单价 = 总成本 / 有效产量
```

建议在批次录入页给出「投料重量 → 成品重量」双输入框，自动算出品率。

---

#### 4. 目标毛利率 → 建议售价

**价值**：目前应用止步于「算出成本」，而工厂下一步必然是「该报多少钱」。加上毛利率这一步，工具就从计算器升级为报价助手，是 B 端的刚需。

**实现**：成本结果卡片下方追加一行「建议出厂价」：

```
建议售价 = 吨价 ÷ (1 - 毛利率) ÷ (1 - 税率)
```

毛利率可在产品级配置（不同产品线毛利要求不同）。

---

#### 5. 「复制为新的批次」/ 配方模板

**价值**：试产迭代时，80% 的配料是不变的，只调整一两种。目前每次都要重新逐个添加，是最高频的重复劳动。

**实现**：批次详情页加「以此配方新建」，预填全部配料，用户只改差异项。进一步可做「配方模板」—— 把验证通过的批次存为模板，一键套用。

### 第二梯队：体验与洞察升级

#### 6. 成本趋势折线图

目前批次间对比只有「↑3.2%」这样的离散数字。用折线图（如 Vico 或 MPAndroidChart）展示吨价随批次的变化，配合时间轴，一眼看出成本走势。对管理者汇报场景价值很高。

#### 7. 配料成本占比分析

饼图/条形图展示各原料占总成本比例，并按占比降序。直接回答「该从哪降本」—— 例如发现某香精占总成本 40%，替代方案的收益一目了然。

#### 8. 产品列表页的成本概览

`CostRepository` 里已定义好 `ProductSummary`（批次数、最新批次、平均/最低/最高吨价）却从未使用。在产品卡片上直接展示，配合按品类筛选，让首页从「产品目录」变成「成本看板」。

#### 9. 单位体系扩展

当前只支持 `元/kg` 和 `元/g`。实际采购中还有：

- **元/吨**（大宗原料：白砂糖、面粉）
- **元/L**（液体原料：糖浆、果汁、食用油）—— 需要引入**密度**字段换算
- **元/件**（包材：瓶、盖、标签按个买）

建议抽象为 `PriceUnit` 枚举 + 换算表，集中到 Rust 引擎，避免换算逻辑在 UI 层散落。

#### 10. 报表导出（Excel / CSV / PDF）

工厂的成本数据最终要流向：给领导汇报、给客户报价单、存档。支持按产品/时间范围导出，是 B 端工具商业闭环的最后一环。PDF 成本单还应支持直接打印/分享到微信。

---

### 第三梯队：差异化能力

#### 11. 原料价格联动预警

原料库单价更新时，反向扫描引用了该原料的历史批次，提示「草莓单价从 ¥12 调整为 ¥14，影响 8 个批次，最新成本将上升 5.3%」。让原料库从静态字典变成活的成本中枢。

#### 12. 敏感性分析（What-if）

「如果白糖涨价 10%，吨价会变成多少？」—— 滑动条调整单个或多个原料价格，实时预览成本变化。对采购谈判和配方调整决策很有价值。计算量小，可完全在 Rust 引擎内完成。

#### 13. 配料表合规与排序（GB 7718）

国标要求配料表按加入量递减排序。目前 `BatchIngredient` 已记录用量，可自动生成合规排序的配料表文本，并校验是否超过添加剂限量（如 GB 2760）。这是食品行业特有的合规刚需，竞品很少覆盖。

#### 14. 保质期推算

`Ingredient.shelfLifeDays` 字段已存在但未使用。可按「最短保质期原料」推算产品保质期，结合生产日期给出到期提醒。

#### 15. OCR 能力深化

当前 OCR 只识别配料**名称**入库。可进一步识别营养成分表（能量/蛋白质/脂肪/碳水/钠），自动填充 `BatchResult` 的理化指标，大幅减少手工录入。

## 四、建议执行顺序

```
第一批（正确性，1 周内）
  ├─ P0-2  saveBatchWithIngredients 补事务          ← 数据一致性，风险最高
  ├─ P0-3  表单状态 rememberSaveable / 提升到 VM     ← 用户可感知
  ├─ P0-4  totalCost 默认值 + 工厂函数               ← 防止成本静默算错
  └─ P0-1  详情页 N+1 → @Relation                   ← 性能，随时间劣化

第二批（健壮性）
  ├─ 功能-2 数据备份与恢复                          ← 离线应用生命线
  ├─ P1-5   统一错误处理
  ├─ P1-6   WhileSubscribed
  └─ P1-7   清理死代码

第三批（能力升级）
  ├─ 功能-1 加工费计算                              ← 引擎已就绪，补齐即可
  ├─ 功能-3 出品率
  ├─ 功能-5 复制批次
  └─ 功能-4 毛利报价

第四批（工程化）
  ├─ P2-11  Room 迁移测试（重要！）
  ├─ P2-12  R8 + exportSchema
  └─ 功能-6/7 图表与洞察
```

**一句话总结**：这个项目的架构底子（Rust 引擎 + 等价回退 + 完整迁移链）比大多数同规模应用扎实，主要风险集中在**数据层的事务与查询效率**、**UI 状态的生命周期管理**，以及**成本计算的隐式约定**（单位、默认值）上。功能上最值得优先做的是**加工费**和**数据备份** —— 前者让工具真正可用于生产报价，后者是离线应用不可回避的责任。
