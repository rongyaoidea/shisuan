## 一、代码质量建议

### P0 — 影响正确性，建议立即修

#### 1. 原料单价会被静默清零 ★ 本报告最严重发现

**位置**：`CostRepository.saveIngredientByNameAndBrand`（CostRepository.kt:214-240）

```kotlin
return if (existing != null) {
    db.ingredientDao().update(
        existing.copy(
            category = category.ifEmpty { existing.category },
            unitPrice = unitPricePerKg,   // ← 无条件覆盖！
            ...
```

`IngredientUpsert` 的注释写明「unitPricePerKg=0 表示暂不设置」，但实现没有兑现。两条真实触发路径：

- **OCR 批量入库**：`ProductViewModel.kt:361` `saveIngredients(names.map { IngredientUpsert(name = it) })` —— 用户用 OCR 识别一张配料表，只要图片里出现**原料库中已存在的原料名**，该原料的单价就被改写成 0；
- **快速添加留空价格**：`IngredientPickerSheet` 中参考单价留空 → `toDoubleOrNull() ?: 0.0` 同样触发。

单价为 0 的原料进入批次后 `totalCost = 0`，成本被**静默低估**，且用户毫无感知——对成本核算工具而言这是最致命的故障模式。

**修复**（一行）：

```kotlin
unitPrice = if (unitPricePerKg > 0.0) unitPricePerKg else existing.unitPrice,
```

配套补一个单测：先保存 12 元/kg 的「白砂糖」，再以 0 价 upsert 同名原料，断言单价仍为 12。

#### 2. 编辑/复制批次时旋转屏幕，表单会被数据库旧值覆盖重置

**位置**：`NewBatchScreen.kt:100-111`

```kotlin
LaunchedEffect(editBatchId) {
    if (editBatchId != null) viewModel.loadBatchForEdit(editBatchId)
}
LaunchedEffect(copyFromBatchId) {
    if (copyFromBatchId != null) viewModel.copyFromTemplate(copyFromBatchId)
}
```

表单状态已提升到 ViewModel（正确），但 `LaunchedEffect` 在**每次重组进入时都会重新执行**。旋转屏幕 → Activity 重建 → Composable 重新进入组合 → `loadBatchForEdit` / `copyFromTemplate` 再次运行 → `fillFormFrom` 用数据库值**覆盖用户已修改但未保存的内容**。状态存 VM 的收益被这一行抵消了。

**修复**：加「已加载」守卫，同一批次只加载一次：

```kotlin
// NewBatchViewModel
private var loadedEditBatchId: Long? = null

fun loadBatchForEdit(batchId: Long) {
    if (loadedEditBatchId == batchId) return   // 已在草稿态，不覆盖
    loadedEditBatchId = batchId
    _editBatchId.value = batchId
    ...
}
// copyFromTemplate 同理记录 copiedFromBatchId；resetForm/clearEditMode 时清空
```

#### 3. 点「保存批次」后立即导航返回，保存协程可能被取消 —— 丢单无提示

**位置**：`NewBatchScreen.kt:423-431`

```kotlin
onClick = {
    ...
    viewModel.saveBatch(productId = productId, batchDate = date)  // fire-and-forget
    onNavigateBack()   // ← 立即弹栈
}
```

`saveBatch` 内部是 `launchSafe` 异步执行，而 `onNavigateBack()` 同步弹出导航节点。弹栈会销毁该 NavBackStackEntry 的 ViewModelStore → `viewModelScope` 取消。轻则保存完成前协程被取消（**批次静默丢失**），重则事务回滚到一半；若 DB 抛错（约束冲突、磁盘满），Snackbar 挂在已被销毁的页面上，**用户永远看不到错误**。

**修复**：把「保存成功」变成导航条件。最小改动：

```kotlin
// ViewModel：改为挂起函数并返回结果
suspend fun saveBatch(productId: Long, batchDate: String): Boolean = withContext(Dispatchers.IO) {
    try { ...repo.saveBatchWithIngredients(...); resetForm(); true }
    catch (e: CancellationException) { throw e }
    catch (e: Throwable) { _error.value = e.userMessage(); false }
}

// Screen：用 rememberCoroutineScope 触发，成功才返回
val scope = rememberCoroutineScope()
Button(onClick = {
    scope.launch {
        val ok = if (isEdit) viewModel.updateBatch(date) else viewModel.saveBatch(productId, date)
        if (ok) onNavigateBack()
    }
}, ...)
```

`updateBatch` 同样处理。这也是自动化测试「保存失败不跳页」的前提。

### P1 — 数据安全与体验硬伤

#### 4. MIGRATION_1_2 引用已被删除的列，v1 存量用户升级即崩

**位置**：`CostCalDatabase.kt:310-315`（迁移 1→2 第 7 步）

```sql
INSERT INTO batch_ingredient (...)
SELECT id, '原料总成本(迁移)', sampleWeightGram, materialCost / sampleWeightGram, materialCost
FROM (SELECT id, sampleWeightGram, materialCost FROM batch_record WHERE materialCost > 0)
```

该语句在 `DROP TABLE batch_record` + `RENAME batch_record_new TO batch_record` **之后**执行，而新表根本没有 `materialCost` 列 → SQLite 在**语句预编译期**就抛 `no such column: materialCost`（与表里有没有数据无关）→ 迁移失败 → 应用启动即崩，且每次启动重试永远失败（迁移砖化）。

**修复**：把「创建 batch_ingredient + 迁移旧 materialCost」两步**挪到 DROP/RENAME 之前**执行（旧表还在，列可读）。若确认 v1 从未发布给用户，至少加注释说明并顺手修正，避免未来复用此迁移模式时踩坑。

#### 5. OCR 链路三连：吞异常、全尺寸解码、忽略 EXIF 旋转

**位置**：`OcrAnalyzer.kt:34-60`

- `catch (e: Exception) { emptyList() }` 把识别失败与「图片里没有配料」混为一谈，调用方 `recognizeIngredients` 对空列表不做任何提示——用户扫码后毫无反应，不知道该重试还是该放弃。应返回 `Result<List<String>>`，失败时 UI 明确提示「识别失败，请重拍」；
- `BitmapFactory.decodeStream` 无 `inSampleSize` 降采样：一张 1200 万像素照片解码为约 48MB 位图，低端机 OOM 风险高、识别慢；
- `InputImage.fromBitmap(bitmap, 0)` 写死旋转 0°，相机直拍的照片带 EXIF 旋转时文字方向错误、识别率骤降。

三问题一个改法解决：改用 `InputImage.fromFilePath(context, uri)`（框架自动处理 EXIF 与降采样），并让 `recognizeIngredientNames` 返回 `Result`。

#### 6. 版本时间线的「当前」标记在恢复后会指错对象

**位置**：`ProductDetailScreen.SnapshotHistorySheet`（`isLatest = index == 0`）

把批次恢复到旧版本后，时间线上标「当前」的仍是**版本号最大**的那条，而实际内容已经回到旧版本。语义应当是「内容与当前批次一致的版本」才是当前。修复：进入时间线时对当前批次+配料算一次 `BatchSnapshotCodec.digest`，与各快照 digest 匹配者标「当前」，其余恢复按钮放开（包括比当前版本新的）。

## 二、功能拓展建议

上轮 15 项中已落地 8 项（加工费、备份、出品率、毛利报价、复制批次、趋势图、占比图、重量显示换算）。以下按「用户价值 ÷ 实现成本」重新排序，并补充结合现有新架构（快照链、批次差异、品牌配料库）才有条件做的新建议。

### 第一梯队：补全成本工具的「最后一公里」

#### 1. 单价单位体系扩展 ★ 引擎层就该有

现状只支持 元/kg、元/g。真实采购里：白砂糖按**元/吨**、糖浆果汁按**元/L**（需密度换算）、瓶盖标签按**元/件**。建议：

- `Ingredient.priceUnit` 扩为受控枚举（`元/kg | 元/g | 元/t | 元/L | 元/件`），新增 `densityGPerMl` 字段（液体原料）；
- 换算逻辑**下沉到 Rust 引擎**（`unit_price_to_total(weight, price, unit, density)`），保持单一计算真相——目前 Kotlin `CostCalculator.unitPriceToTotal` 只认 `isPerGram` 布尔，扩展后布尔参数无法表达 5 种单位；
- 注意 `saveIngredientByNameAndBrand` 硬编码了 `priceUnit = "元/kg"`，扩展时一并参数化。

#### 2. 成本单导出（CSV / PDF）

备份导出已打通 SAF 全链路（文件选择器、权限、错误处理），在其上做业务导出成本很低：

- 批次/产品级 CSV：配料明细 + 成本构成，Excel 直接可开，给采购与财务；
- PDF 成本单：吨价/箱价/包价 + 建议出厂价，可直接打印或分享微信，用于对外报价。
- 这是 B 端工具商业闭环的最后一环。

#### 3. 产品列表 = 成本看板

`ProductSummary`（批次数/最新吨价/最高最低）在 9/4 就已写好但从未接线。产品卡片直接展示「最新吨价 + 近 5 批涨跌」，配合品类筛选，首页从产品目录升级为管理看板——对老板角色，这是打开应用的第一个理由。

#### 4. 配方变体对比（A/B 试验组）

当前差异对比只有**时间轴相邻批次**一种维度。试产场景常见「同一天做两个配方变体」，需要并排对比两组批次的成本与差异。数据结构（配料明细、快照）已完全支持，缺的只是 UI：批次卡加「对比」模式，选中 2~N 个批次并排展示吨价/箱价/包价与分项差异。

#### 5. 建议出厂价支持含税口径

`suggestedTonPrice = 吨价 ÷ (1 - 毛利率)` 未含税。B 端报价通常要区分未税/含税（13% 增值税）。产品级加一个 `taxRate` 字段，报价行展示双口径，改动仅限引擎一个函数 + 一个字段。

### 第二梯队：让存量数据「活」起来

#### 6. 原料价格联动 + What-if 敏感性分析

原料库调价时反向扫描引用该原料的批次提示影响面（「白砂糖 ¥12→¥14，影响 8 个批次，最新吨价 +5.3%」）；进一步做滑杆式 What-if：拖动任一原料价格实时预览吨价变化。两者都是 Rust 引擎内的小计算，配料明细结构已就绪。

#### 7. 批次成果与问题记录 UI（激活两张空表）

`BatchResult`（口感/颜色/pH/糖度/评分）与 `BatchProblem`（分类/原因/对策）建表已久无 UI。补上后：好批次（评分高）与成本数据关联，回答「哪个配方既好又便宜」。OCR 可顺势深化——识别**营养成分表**自动回填 pH/糖度等理化指标，减少手工录入。

#### 8. 配料表合规辅助（GB 7718 / GB 2760）

配料已记录克重，可自动按投料量递减生成合规配料表文本；有添加剂限量库时可做超限校验。食品行业特有刚需，竞品覆盖少，且计算全在本地。

#### 9. 保质期推算

`Ingredient.shelfLifeDays` 字段闲置中。按「最短保质期原料」推算产品保质期，结合批次日期给到期提醒。

#### 10. 版本历史 Diff 视图

快照链已存下每次变更的完整内容，但目前只能「整体恢复」。加一个两版本对比视图（配料增删高亮、用量/单价变化标红绿），把「git log」升级成「git diff」，排障与复盘价值都会上一个台阶。

### 第三梯队：长期方向

- **多设备数据合并**：工厂里多台手机各录各的批次，目前整库导入会互相覆盖。基于快照链的 digest 做按批次合并导入（冲突时保留双份让用户选），离线应用演化为弱协同。
- **产线/车间维度**：`BatchRecord` 增加产线字段，同一配方不同产线的成本对比。等真实用户提出再做，避免过度设计。
- **深色模式与车间大字模式**：Theme.kt 目前仅浅色。车间强光下浅色合理，但凌晨班次与低视力用户需要大字号——至少把关键数值的字体做可调。

### 便捷性设计：快捷输入组件体系（功能不减、输入减负）

新增 `ui/components/InputControls.kt` 四组件，**键盘输入全部保留**作为精确通道，快捷方式只是加速：

| 组件 | 形态 | 用途 |
|------|------|------|
| `StepperNumberField` | 输入框 + −/＋ 步进按钮 | 有明确粒度的数值（克重、价格、加工费），按 `step` 增减，自动按 step 定小数位 |
| `SliderNumberField` | 滑条 + 数值输入框 | 有自然区间的数值（出品率、毛利率、pH、糖度），`increment` 控制档位 |
| `QuickChipsRow` | 常用值标签（FilterChip） | 一键填入行业常用值，点击即选中 |
| `TextChipsRow` | 文本标签 | 品类/口感/颜色等枚举值，再点已选项即清除 |

接入点（五处）：

1. **新建/编辑批次页**：样品重量 ±10g 步进 + 100/250/500/1000/2000g 标签；出品率 50–100% 滑条 + 80/85/90/95% 标签；加工费三项 ±1 元步进；配料克重 ±1g + 常用克重标签、比例 ±0.01% + 常用比例标签；
2. **配料选择器**：新增搜索框（按名称/供应商即时过滤，空匹配提示）＋ 快速加原料品类标签（水果/糖类/添加剂/乳制品/包材/其他）＋ 价格 ±0.5 元/kg 步进；
3. **新建/编辑产品**：品类标签（果酱/酱料/调味品/罐头/烘焙/其他）、每箱包数/每包克数步进 + 常用克重标签、毛利率 0–60% 滑条 + 20/30/40/50% 标签；
