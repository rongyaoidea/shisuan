## 一、修复清单（本次提交）

### 1. BackupManager.importFrom「先删后拷」非原子替换 ★ 本次最严重发现

**文件**：`app/src/main/java/com/example/shisuan/data/backup/BackupManager.kt`

**问题**：恢复备份时原实现为 `File(dbPath).delete()` → `staging.copyTo(File(dbPath))`。两步之间存在一个数据丢失窗口：若拷贝中途失败（IO 错误、存储空间不足、进程被杀），**旧数据库已删、新数据库未写完，用户全部产品与批次历史永久丢失**。对一个「数据只存本机、无云端兜底」的离线应用，这是灾难级故障。

**修复**：改为 `staging.renameTo(File(dbPath))` 原子替换。staging 位于 cacheDir、主库位于 databases 目录，同属应用私有存储同一分区，`rename(2)` 为原子操作——即使进程在替换瞬间被杀，留下的也是完整的旧库或完整的新库，不存在中间态。`-wal`/`-shm` 残留日志在 rename 前删除，rename 失败时抛 IOException 由 Snackbar 提示重试。

**附带说明**：原代码的 staging 校验（SQLite 魔数 + schema 版本）设计得很好，本次仅替换落盘方式，校验链路不变。

### 2. 配料占比环形图：图例颜色与扇区不对应

**文件**：`app/src/main/java/com/example/shisuan/ui/components/Charts.kt`（IngredientCostDonut）

**问题**：扇区按 `items` 传入顺序依次取色（`forEachIndexed` 原始 index），而图例按成本**降序排序后**重新取色（`sortedByDescending` 后的 index）。两者只有当数据恰好已按占比降序传入时才一致；否则图例声称「草莓=红」，图上草莓扇区却是橙色，视觉直接误导用户。

**修复**：图例改为 `items.withIndex().sortedByDescending { it.value.second }`，排序仅影响排列顺序，色块沿用各配料在扇区中的原始顺序色，保证一一对应。

### 3. Rust calc_differential 缺 current 有限性防御

**文件**：`shisuan-rs/src/calc.rs`

**问题**：`calc_differential` 只校验了 `prev` 的有限性，`current_ton` 传 NaN 时会返回 `Some(NaN, NaN, false)`，NaN 经 JNI 写入 out 数组直达 UI（批次卡片显示「↑ NaN%」）；传 +Inf 显示「Infinity」。

**修复**：函数入口增加 `if !current_ton.is_finite() { return None; }`，非有限输入按「无对比数据」处理（JNI 返回 1，UI 不显示差异）。`lib.rs` 测试新增 3 条 NaN/Inf 用例。

### 4. Kotlin 回退实现与 Rust 引擎行为漂移

**文件**：`app/src/main/java/com/example/shisuan/utils/CostCalculator.kt`

**问题**：Rust 版 `unit_price_to_total` 对 `weight<=0 || unitPrice<0` 返回 0.0，而 Kotlin 回退版（单测环境/so 加载失败时生效）无此检查，负单价会算出负成本、NaN 会传播。同一输入在「真机」与「单测」两条路径结果不同，正是注释里自己声明要避免的「双实现漂移」。`calcDifferentialKotlin` 同样缺 current 非有限防御。

**修复**：回退版 `unitPriceToTotal` 补齐 `weightGram <= 0.0 || unitPrice < 0.0 || 非有限` → 0.0；`calcDifferentialKotlin` 补 `!currentTonCost.isFinite()` → null。与 Rust 语义完全对齐。

### 5. JNI 桥接层 out 数组防御加固

**文件**：`shisuan-rs/src/jni_bridge.rs`

**问题**：`calculate` / `calcDifferential` 直接 `unsafe { JDoubleArray::from_raw(out) }` 后写回：out 为 null（Java 侧调用方违约时）会导致 JVM SIGSEGV；out 长度不足时依赖 JNI 规范的越界异常兜底，不够显式。

**修复**：两函数入口增加 `out.is_null()` 检查与 `get_array_length` 长度校验（calculate 要求 ≥5、calcDifferential 要求 ≥3），不满足返回新错误码 `ERROR_INVALID_ARGS(2)`。Kotlin 侧 `CostCalculator` 对非 0 返回码统一回退 Kotlin 实现，降级路径天然闭合。正常调用路径（固定传 `DoubleArray(5)`/`DoubleArray(3)`）行为不变。

## 三、审查确认的良好实践（保持）

- **双实现漂移防线设计正确**：出品率折算在上层 `effectiveWeightGram` 统一完成后才进入引擎，JNI 签名不含出品率，Rust 与 Kotlin 公式天然一致（本次漂移是防御分支缺失而非公式不一致，已对齐）。
- **Room 迁移链 v1→v9 完整可测**：schema JSON 随 debug/androidTest assets 打包，Robolectric `MigrationTest` 在 JVM 上即可验证迁移，不依赖真机。
- **批次快照版本链**：SHA-256 内容指纹去重 + `digest+version` 唯一索引 + 恢复后再恢复的双向时间线，设计成熟；「当前版本」按 digest 匹配而非按 version 最大值，恢复语义正确。
- **保存流程无静默丢单**：`saveBatch`/`updateBatch` 带 `_saving` 防重入、事务内 `captureSnapshotLocked`、成功后才 `onResult(true)` 导航返回，失败留页 + Snackbar 原因。
- **错误处理链**：`BaseViewModel.launchSafe` 正确重抛 CancellationException（不破坏结构化取消）；异常翻译为用户可读文案，不泄漏表名/SQL。
- **OCR 模块**：`InputImage.fromFilePath` 自动处理 EXIF 方向与降采样（避免 OOM 与旋转错误）；失败与「成功但无配料」两态区分；相机探测在 Manifest 中正确声明 `<queries>` 兼容 Android 11+ 包可见性。
- **R8/ProGuard 规则完备**：JNI native 方法、Room 实体、行号保留均有显式 keep，注释解释了每条规则的存在原因。
- **CI**：tag 触发签名构建 + JVM 单测（含 Robolectric 迁移测试）门禁 + 自动 Release；`workflow_dispatch` 支持链路验证。
- **测试覆盖**：9 个 JVM 测试文件覆盖计算、快照编码、日期换算、OCR 解析、迁移；Rust 侧 `cargo test` 覆盖核心公式与边界（本次新增 NaN/Inf 用例）。
